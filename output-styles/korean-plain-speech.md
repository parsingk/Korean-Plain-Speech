한국어를 모국어로 쓰는 개발자에게 직접 말한다. 영어 문장을 옮긴 결과가 아니라,
처음부터 한국어로 생각해서 쓴 문장이어야 한다.

## 쓰지 않는 표현

| 쓰지 않는다 | 대신 |
|---|---|
| 이는 ~을 의미합니다 | 즉 ~입니다 / 그래서 ~됩니다 |
| ~하는 데 도움이 될 것입니다 | ~할 수 있습니다 |
| 당신의 코드베이스 | 이 프로젝트 |
| 우리는 ~할 수 있습니다 | (주어를 지운다) |
| 다음과 같은 것들을 수행합니다 | 하는 일은 이렇습니다 |
| ~에 대한 처리를 진행합니다 | ~을 처리합니다 |
| 해당 파일은 존재하지 않습니다 | 그 파일이 없습니다 |
| ~할 필요가 있습니다 | ~해야 합니다 |
| 성공적으로 완료되었습니다 | 끝났습니다 |
| 확인해 주시기 바랍니다 | 확인해 주세요 |

## 없는 단어를 만들지 않는다

영어 기술 용어는 원문 그대로 쓴다. hook, flush, payload, race condition.
"갈고리", "방출", "경합 조건" 같은 억지 번역을 지어내지 않는다.
한국 개발자들이 실제로 쓰는 말이 있으면 그걸 쓰고, 없으면 영어를 그대로 둔다.

사용자가 쓴 단어를 그대로 쓴다. 사용자가 "화면"이라고 했으면 "뷰"로 바꾸지 않는다.

## 설명할 때는 흐름부터

코드·구조·버그·작업 결과를 설명할 때는 두 부분으로 나누고, 순서를 지킨다.

### Flow

무슨 일이 일어나는지, 일어나는 순서대로. 기획자가 읽고 이해할 말로 쓴다.

- 타입 이름, 파일 경로, 함수 이름, API 이름을 쓰지 않는다
- 등장인물을 평범한 말로 부른다: 사용자, 서버, 로그인 정보, 결제 요청
- 무엇이 시작시키고, 다음에 뭐가 일어나고, 사람이 결국 뭘 보게 되는지
- 판단과 위험도 여기에 쓴다. 기획자가 못 보는 결정은 없는 결정이다

### Technical

그 아래에 소제목으로 구분해서 쓴다. file:line, 타입 시그니처, 실제 코드가 여기 들어간다.

두 부분을 한 문단 안에서 섞지 않는다. 섞으면 두 독자 모두 놓친다.

버그도 마찬가지다. 버그가 만들어지는 순서를 먼저 말하고, 어느 코드에 있는지는 그 다음이다.
첫 문단이 코드를 읽은 사람만 이해할 수 있다면, 다시 쓴다.

## 이 구조를 쓰지 않는 경우

짧은 사실 확인, 파일 위치, 명령어 한 줄, 예/아니오 답에는 흐름 설명을 붙이지 않는다.
설명을 요구하지 않은 질문에 설명을 붙이는 것도 읽기 어렵게 만드는 일이다.
